1. 
Document Review
This document provides a comprehensive technical and functional overview of the Shipping Bill API Integration process, which is a key digital workflow for port operations within the ODeX platform. Shipping Bill is a critical document used in Indian ports (e.g., JNPT, Mundra, etc) for onboarding permissions of containers, and this documentation aims to guide technical teams, integration partners, and stakeholders through its end-to-end automation.
The manual is intended to support both API consumers (such as shipping lines or third-party software vendors) and system implementers by detailing the process of submitting, validating, and managing Shipping Bill data via secure RESTful APIs.
Objectives:
To outline the structure, data flow, and system interactions required for successful Shipping Bill integration.
To define API request/response standards, including field-level rules, mandatory checks, and sample payloads.
To ensure consistency and error-handling mechanisms across all Shipping Bill submissions.
To support faster onboarding of external systems or clients integrating with ODeX.
Audience:
Backend/API Developers
Integration Teams of Shipping Lines/Agents
Business Analysts and Project Managers
QA Teams involved in testing integration
ODeX Internal IT & Support teams
2. Business Use Case
Shipping Bill (SB) is a mandatory document issued by shipping lines which serves as a declaration to customs authorities, providing details about the goods being shipped, their value, quantity, and destination. This document is essential for customs clearance, facilitating the movement of goods out of the country, and plays a vital role in claiming duty drawbacks and export incentives. Traditionally handled via email or manual systems, Shipping Bill is now being digitized through API integration to improve turnaround time, reduce manual errors, and ensure regulatory compliance.
The Shipping Bill Integration enables seamless, real-time submission of requests directly from the Payor's internal system to the ODeX System. This not only simplifies submission of Shipping Bill requests but also enhances operational efficiency, especially in high-volume export scenarios.

4. High-Level Architecture
Overview:
This section outlines the data flow between a Payor, ODeX platform, and the shipping line for successful Shipping Bill processing via APIs.
Steps Explained:
Shipping Bill Submission: The Payor's system sends a POST request with container gate-in details.
Validation & Processing (ODeX): ODeX validates Vessel, POD, Terminal against Master APIs and Mandatory fields and format.
Visibility of request on ODeX for Shipping Line: Upon successful validation, ODeX forwards the Shipping Bill response back to the Payor.

7.4 Shipping Bill Amendment API
The Shipping Bill Amendment API enables registered users to withdraw or update a previously submitted Shipping Bill request for export operations. This functionality is essential in scenarios where the original submission contains incorrect information, operational plans change, or the request was submitted in error or duplicate. Amendment can be initiated, provided the Shipping Bill is in an active state such as 'Verified' or 'Confirmed'.
In cases where the request has already been confirmed, a structured Request for Amendment (RFA) workflow is followed, requiring approval from the relevant Liner authority. The amendment process ensures data integrity, prevents unauthorized access, and facilitates resubmission of corrected Shipping bill details where necessary.
Status
Description
Requested
The Shipping Bill request has been submitted by the Payor but is yet to be verified or acted upon.
Verified
The Shipping bill request has been validated for correctness and meets all required criteria.
Confirmed
Shipping bill has been formally approved by the Liner or the system and is ready for operational use.
Rejected
The Shipping bill request has been rejected due to invalid data, non-compliance, or operational reasons.
Amendment Requested
An amendment request has been initiated after confirmation, pending approval.
Amendment Approved
The amendment request has been approved, and the Shipping bill is officially updated.
Amendment Rejected
The amendment request has been denied, and Shipping bill remains as previously confirmed.

11. FAQ's
Q1. Who can use the Shipping Bill Integration API?
A. The API is designed for Payors (Exporters/CHA) and integration partners who want to automate Shipping Bill submissions through the ODeX platform.
Q2. What type of APIs are provided under this integration?
A. The integration offers:
Master APIs 
– 
for validating vessel, port, and terminal data.
Transaction API 
– 
for submitting Shipping Bill data.
Response/Status APIs 
– 
for checking submission status and receiving error/success messages.
Amendment API 
– 
for modifying already submitted Shipping Bills (subject to status).
Q3. What authentication mechanism is used?
A. Authentication is managed via API secret Key/Token (shared securely by ODeX). All requests must be sent over HTTPS.
Q4. What environments are available for testing and live use?
A. ODeX provides two environments:
UAT 
– 
for integration testing. Base URL: https://staging.odexglobal.com/RS/iEGMService/
Production 
– 
for real-time operational use. Base URL: https://www.odexglobal.com/RS/iEGMService/
Q5. What file formats are supported for attachments?
A. Currently, only PDF files are allowed as attachments. The file should be converted to a byte array (Base64 encoded) with a maximum size limit of 5 MB per file and total size not exceeding 4 MB.
Q6. How can I check the status of a submitted Shipping Bill?
A. You can use the Get Shipping Bill Status API by providing the Booking No, Shipping Line BNF Code, Payor Code and Gateway Location to retrieve the latest status.
Q7. What happens if a Shipping Bill is rejected?
A. The rejection reason will be provided in the remarks / business_validations field of the API response. The Payor can then correct the errors and resubmit the Shipping Bill.
Q8. Can I amend a Shipping Bill after submission?
A. Yes. Amendments are allowed if the Shipping Bill is in Verified or Confirmed state. For confirmed requests, an Amendment Request workflow is initiated that requires liner approval.
Q9. What are the common reasons for validation errors?
A. Common errors include missing mandatory fields (e.g., Booking No, Vessel Name, FPOD), invalid codes (Shipping Line, Location, Cargo Type), incorrect data formats (dates, container numbers), and mismatches with ODeX Master Data.
Q10. What is the maximum number of containers allowed in a single Shipping Bill request?
A. Multiple containers can be submitted in a single request. Each container's details (Container No, Shipping Bill No, etc.) must be repeated under the egmRequestcntnrVoList array of the request.
Q11. What is odexRefNo and why is it important?
A. The odexRefNo is a unique reference number generated by ODeX for every request. It must be retained and used for future queries, status checks, and amendments related to that request.
